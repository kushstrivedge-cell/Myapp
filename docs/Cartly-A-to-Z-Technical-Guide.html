1. Project overview and present status

Cartly is a React Native retail application inspired by large marketplace apps. The mobile client provides the shopping interface; the Express server owns authentication and catalogue rules; PostgreSQL stores durable data; Prisma provides typed database access. The app is currently Android-tested, but its React Native structure also contains the standard iOS project.

Important: the database schema already models most future ecommerce entities. A table existing in Prisma does not mean its API is implemented. At this edition, authentication, catalogue, account and address modules are real server modules.

2. System architecture and request flow

Samsung Android phone │ React Native screens and components │ Context providers (auth, catalogue, cart, etc.) │ apiClient: JSON + Bearer token + refresh/retry ▼ Express API on laptop, port 4000 │ Zod validation → middleware → service │ Prisma Client through PostgreSQL adapter ▼ PostgreSQL 18, database: myapp, port 5432

During development, ADB reverse maps the phone’s localhost:4000 to the laptop’s port 4000 and localhost:8081 to Metro. This works over USB and Android Wireless Debugging. Therefore the source code can keep using http://localhost:4000/api/v1 without hard-coding a changing Wi-Fi address.

Typical product request

CategoriesScreen → useCatalogue().listProducts(filters) → catalogueApi.products() → apiGet('/products?...') → Express catalogue route → Zod query validation → catalogueService.products() → Prisma queries PostgreSQL → JSON envelope → API model mapped to mobile CatalogueProduct → FlatList renders ProductCard

4. How the app starts

  1. index.js imports App.tsx and registers it with React Native.
  2. SafeAreaProvider handles notches and system bars.
  3. NetworkProvider subscribes to NetInfo and shows the offline banner.
  4. AuthProvider reads encrypted tokens from Android Keystore through Keychain.
  5. If tokens exist, the backend refresh endpoint rotates them and restores the user.
  6. CatalogueProvider loads categories and the initial popular product list.
  7. Other providers expose local cart, checkout, orders, notifications, search, wishlist and address state.
  8. NavigationContainer renders the root navigator and initial Home tab.

While the session is being restored, AsyncStateView displays a full-screen progress indicator. A network failure presents a retry action without deleting saved credentials.

7. Shared API client and offline behavior

src/services/apiClient.ts is the single transport layer. Feature wrappers such as authApi and catalogueApi describe endpoints without repeating fetch/error/token code.

Authenticated request lifecycle

Read tokens from Keychain → Attach Authorization: Bearer accessToken → Send request → If success: parse { success, data } → If 401: use refreshToken once → Store rotated token pair → Retry original request once → If refresh is invalid: clear tokens and sign out → If refresh failed only due to network: keep tokens

A shared refresh promise prevents five simultaneous expired requests from creating five token rotations. API errors include HTTP status, backend error code and optional details. Network failures become a consistent NETWORK_ERROR.

ConnectivityBanner uses @react-native-community/netinfo. It shows a global red banner when offline and offers Retry. AsyncButton provides spinner/disabled behavior; AsyncStateView provides full-page loading/error/retry behavior.

8. Registration, OTP, login and token flow

Registration

  1. The mobile app posts name, normalized email, ten-digit phone and password.
  2. Zod requires valid input and an eight-character minimum password.
  3. The server checks for an existing verified email.
  4. Password hashing uses Node scrypt with a random salt; plaintext is never stored.
  5. A random six-digit OTP is hashed and stored with expiry, purpose, attempts and consumed status.
  6. SMTP sends the OTP. Without SMTP in development, it prints in the backend console.
  7. Verification consumes the OTP, marks the email verified and issues an access/refresh token pair.

Login and session restoration

Login verifies the scrypt hash and requires verified email. The short-lived JWT access token authorizes APIs; the longer refresh JWT is stored as a hash in PostgreSQL. The raw token pair is saved in Android Keystore via React Native Keychain. On refresh, the old database token is revoked and a new pair is issued. On logout, the refresh token is revoked and device credentials are cleared.

Password reset

The forgot-password response is deliberately generic to prevent email enumeration. A valid reset OTP changes the hash and revokes every active refresh token for that user.

Never inspect or recover plaintext passwords/OTPs: only secure hashes belong in PostgreSQL. Never paste database, SMTP or JWT secrets into chat, source code, screenshots or Git.

9. Categories, products, search, variants and reviews

The seed creates 6 categories, 10 products, stock-aware variants, initial image URLs and 30 review rows. It is idempotent: rerunning it updates matching slugs/SKUs rather than duplicating them.

Filtering and sorting

The server first filters active products by query/category, includes ordered images and variants, calculates minimum/maximum price, total stock, average rating and review count, then applies price/rating/availability/sale filters and sorting. Finally it returns a page with total count, page count and hasNextPage.

Supported sort values are popular, rating, price_asc, price_desc and newest. Search checks name, description and slug case-insensitively. Category filtering supports the category itself and its immediate children.

Mobile model mapping

catalogueApi.ts maps database DTOs to the UI’s CatalogueProduct. Decimal prices are already converted to numbers by the backend. Relative uploaded-image paths are converted to absolute server URLs. A deterministic color and first-letter fallback are generated if no image exists.

Stock

Each SKU variant has independent color, size, price, old price and stock. Product-level stock is the sum of variants, while inStock is true when at least one variant has stock. Product Details prevents Add to Cart/Buy Now for an unavailable selected variant. Final stock enforcement must also happen in the future cart/order backend.

Reviews

Review reads are public and paginated. Writes require an access token. The database unique constraint on (userId, productId) ensures one review per customer/product; the API uses upsert so resubmission edits it. The mobile details page currently displays server reviews. A review editor UI is still to be added.

10. Express backend architecture

  1. server.ts creates the HTTP server on 0.0.0.0:4000 and handles graceful shutdown.
  2. app.ts disables the Express signature and enables Helmet, CORS and the JSON body limit.
  3. /uploads serves development product files.
  4. /api/health verifies the API process.
  5. /api/v1 mounts auth and catalogue routers.
  6. Routes parse input with Zod, call services and return a standard JSON envelope.
  7. Services contain business rules and Prisma operations.
  8. The error handler converts Zod, application and upload errors into safe responses.

Response format

{
  "success": true,
  "data": { "...": "..." }
}
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed"
  }
}

authenticate validates Bearer JWTs and adds request.auth. authorize('ADMIN') protects image mutation. Authentication and OTP endpoints also use rate limiting.

13. Product image storage and upload

Seed products use HTTPS image URLs. New local uploads use multipart field image, optional alt and optional position. Multer writes a randomized file name into backend/uploads/products. The server checks declared MIME type, 5 MB limit and binary signature for JPEG/PNG/WebP before creating the database row.

POST /api/v1/products/p1/images
Authorization: Bearer ADMIN_ACCESS_TOKEN
Content-Type: multipart/form-data

image    = headphones.png
alt      = Headphones front view
position = 1

The returned path looks like /uploads/products/uuid.png. The mobile mapper prefixes the server origin automatically. Local uploads are ignored by Git. For production, replace filesystem storage with S3, Cloudinary or R2 and store the resulting CDN URL.

cd android
.\gradlew.bat clean
cd ..
npm start -- --reset-cache

Clear all app data (destructive)

18. Security decisions

  • scrypt salted password hashes; no plaintext passwords.
  • OTP hashes with expiry, attempts, purpose and one-time consumption.
  • Short access JWTs and rotating, hashed, revocable refresh tokens.
  • Device token storage through Keychain/Android Keystore.
  • Zod validation on request body/query data.
  • Authentication and role authorization middleware.
  • Rate limiting for auth and OTP abuse.
  • Helmet, controlled CORS, JSON size limit and disabled Express signature.
  • Restricted upload MIME, size, filename and binary signature.
  • .env and uploaded development files excluded from Git.
Production note: card number/CVV must never be stored or processed directly by Cartly. Use a PCI-compliant gateway such as Razorpay or Stripe and verify payments through signed server webhooks.

19. What remains for a production ecommerce app

  1. Persistent cart/wishlist: guest cart, login merge, quantity/stock checks and server coupons.
  2. Order engine: server totals, database transaction, inventory reservation/deduction, idempotency and order APIs.
  3. Payments: gateway checkout, backend verification, webhooks, failure recovery and refunds.
  4. Fulfilment: status events, tracking, cancellation eligibility, returns, pickup and refund workflow.
  5. Notifications/support: Firebase push, transactional email, persistent inbox and tickets.
  6. Admin: dashboard and CRUD for catalogue, inventory, orders, users, coupons, reviews and returns.
  7. Production media: cloud object storage, resizing, thumbnails, CDN and image deletion jobs.
  8. Operations: hosted PostgreSQL, HTTPS API, secrets manager, migrations, backups, logs, monitoring and alerts.
  9. Quality: more screen/component tests, isolated test database, end-to-end checkout tests, accessibility and performance.
  10. Release: app identity/assets, signing, privacy/account deletion, analytics, crash reporting and Play Store submission.
Recommended immediate next phase: persistent Cart/Wishlist, followed by transactional Orders and Payments.

20. Quick mental model

When learning or extending Cartly, follow one feature vertically. Start at its screen, find the context hook, inspect the API wrapper, follow the Express route into its service, then inspect the Prisma model. Keep UI state in the screen, shared client state in a context, HTTP behavior in services, business rules in backend services and durable facts in PostgreSQL. This separation is what allows the prototype to grow into a maintainable retail system.

Screen → Context → Mobile API wrapper → Shared apiClient → Express route → Validation/Auth → Service → Prisma → PostgreSQL
